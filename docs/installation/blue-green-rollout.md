# new-api 蓝绿发布与首次双入口迁移方案

> 状态：方案已确定，尚未完成生产切换或全流程验收。本文记录目标架构、两阶段首次迁移及发布前置条件，不是可以直接照抄执行的一键上线脚本。
>
> 最后核对：2026-11-10。发布前必须重新确认实际运行版本、镜像摘要、数据库结构和流量入口。

## 目标与范围

- 同时服务经过 Nginx 域名入口和直接访问宿主机 `56854` 的客户端。
- 保留 Nginx 的域名、TLS 和现有安全策略；最终由一个独立 HAProxy 容器直接占用 `56854`。
- 不增加永久的 `edge-direct` 转发容器，不引入 Kubernetes，也不迁移现有 PostgreSQL、Redis 容器或数据卷。
- 首次迁移分两阶段：先处理域名流量，再在确认的维护窗口接管直连端口。
- 后续兼容版本更新采用 blue/green 切流，保留旧实例上的在途 HTTP、SSE、WebSocket；应用及账务工作完成后才退出旧实例。
- 应用平滑发布不等于跨主机高可用，也不能保证破坏性数据库迁移、代理自身升级或主机故障零影响。

## 最终架构

```text
域名客户端 -> Nginx / TLS --+
直连客户端 ----------------+-> HAProxy :56854
                                  |-> web-blue  (NODE_TYPE=slave)
                                  +-> web-green (NODE_TYPE=slave)

                          worker (唯一 NODE_TYPE=master，不接外部流量)
                                  |
                         现有 PostgreSQL + Redis
```

HAProxy 是独立软件，以 Docker 容器运行；它不是 Nginx 或 Docker 自带的负载均衡功能。日常发布通过其管理 socket 切换后端状态，不重新创建入口容器。

### 角色与配置

- web 槽处理管理 API、登录、支付回调、同步中转及异步任务提交/查询；这些能力必须逐项验证，不能只验证首页可访问。
- worker 承担 master-only 后台任务，不能向外发布端口或接入用户流量。`NODE_TYPE=slave` 不是关闭所有后台 goroutine 的统一开关，额外启用的周期任务仍需单独审查。
- 正式 web 槽不发布宿主机端口，仅首次迁移的 blue 临时发布回环端口 `127.0.0.1:56855`。
- 各实例共用数据库、Redis、固定的 `SESSION_SECRET` / `CRYPTO_SECRET`、兼容的缓存格式及对外 origin/cookie 配置；`NODE_NAME` 必须唯一。
- 配额与鉴权校验继续由服务器执行，不得为兼容切流而关闭鉴权、放宽验证码过期、跳过账务校验或自动重放非幂等付费请求。
- SQL 连接池按所有实例的总量预算配置；不能把单节点连接上限直接复制到多个节点并假定数据库承受得住。
- 请求体临时缓存保持实例隔离；日志按实例区分；持久业务文件/对象存储明确共享范围，不复制容器可写层来替代存储设计。

## 开始前必须满足的条件

### 1. 固定版本及恢复依据

- 构建、检查并记录确切 Git commit、镜像版本、平台、不可变 digest 和实际 image ID；部署不依赖之后可能改变的 `latest`。
- 保留旧容器、旧镜像和原 Nginx/Compose/环境配置，私有状态目录 `0700`、含凭据文件 `0600`，不得写入版本库或打印到日志。
- 在切换前明确每一步失败后的恢复入口；镜像回滚不等于数据库、缓存或业务数据回滚。

### 2. 数据库与迁移

- 数据库仍运行在原容器、原数据卷中，新应用通过原网络连接它，不需要为蓝绿发布搬运数据库文件。
- 备份是为了恢复，不是为了给新应用建立第二份生产库。不能直接复制运行中的 PostgreSQL 数据目录并当作一致性备份。
- 完成可恢复的数据库备份与恢复验证；仅保存 Compose/环境配置不算数据库备份。若演练副本不含大日志表，必须记录遗漏范围，不能声称验证了完整生产迁移。
- 在隔离环境对确切旧版到候选版执行迁移演练，检查锁表、耗时、重复启动、新旧读写兼容性及回滚条件。隔离环境不得发送真实支付、邮件、凭据刷新或付费上游请求。
- 本仓库数据库实现的变更仍须按项目要求通过真实 SQLite、MySQL、PostgreSQL 验证；迁移涉及共享日志库路径时一并覆盖。
- 迁移应有独立、受控的执行阶段。现有 master 启动会同时进行迁移和后台工作，不能把“启动新 master 后马上停止”当作无副作用的 migration-only 命令。
- 不允许用“两个 master 只重叠十几秒、碰撞概率低”替代后台互斥与安全交接。若当前版本不能独立迁移或暂停旧调度，应先补能力或调整维护窗口。

### 3. 应用级排空与账务

- HTTP 连接数为零不能证明批量额度写回、异步退款或后台任务已完成。
- 退出顺序需要停止产生新工作，等待已接受的请求/结算/退款完成，完成最后批量写回并确认持久化成功，最后关闭数据库。
- 不能用固定等待 5 秒或 10 秒代替成功写回的证据。写回失败时不得清空待处理数据并报告排空成功。
- `http.Server.Shutdown` 不等待已 hijack 的 WebSocket；长 SSE 也可能超过默认退出期限，需结合代理及应用层在途工作计数。
- 等待超时保留旧实例，不自动强杀，也不覆盖仍有连接或未完成工作的槽位。
- 后台交接针对当前执行的轮询/结算和可恢复状态，不必等待所有已提交的上游视频任务生成完毕。

### 4. 会话、插件及前端连续性

- 验证码等仍在进程内的跨请求状态不会因共用 Redis 自动共享。必须实现带过期与原子消费的共享状态/兼容过渡，或明确披露并获准对应功能的中断范围；不能承诺整个服务完全无感。
- 验证登录、OAuth、Passkey、会话刷新、注销、权限撤销、支付回调及异步任务跨节点行为，保留过期、重放和敏感操作验证要求。
- 区分进程存活和业务 readiness。当前 `/api/status` 不能证明依赖、插件首轮加载、缓存或排空状态已满足切流条件。
- 验证 Nginx 的 HTTP/1.1、SSE 缓冲/超时、WebSocket Upgrade 透传、真实 IP、Host、HTTPS scheme 和显式可信代理范围。
- 保留旧版本前端 hash 资源并验证新旧 API/UI 兼容，避免已有页面切流后懒加载失败。

## 首次迁移：阶段一，域名流量切到新版

```text
域名 -> Nginx -> 127.0.0.1:56855 -> web-blue（新版 slave）
直连 -> 56854 -> 原容器（仍服务直连，暂时承担唯一 master）
```

1. 满足上述备份、兼容迁移、后台归属与账务前置条件。
2. 启动新版 web-blue，仅临时映射回环端口 `127.0.0.1:56855`，不创建 HAProxy，不争用 `56854`。
3. 验证业务就绪和关键功能，而非只检查首页/状态接口；业务探针使用受控测试账号及合成上游，不默认产生真实计费。
4. 保存 Nginx 原配置，将相关域名 upstream 改到 `56855`，执行配置检查后平滑 reload；不要 restart Nginx。
5. 检查新域名请求进入新版，旧 Nginx worker 与旧后端上的请求继续完成；此阶段原容器不停止，直连入口不变。
6. 观察错误率、流式终止、延迟、额度及任务处理。检查不通过，停止推进，按兼容性条件恢复域名路由。

本阶段的目标是域名请求不中断，不把“平滑 reload”本身当作整个服务已通过零中断验收。

## 首次迁移：阶段二，HAProxy 直接接管 56854

1. 明确低峰维护窗口、直连客户影响及失败回退步骤。只要直连客户仍在旧端口建立请求，就不能假定旧实例会自行完全空闲。
2. 提前准备最终 HAProxy 配置和镜像，验证后端 blue 可达；Nginx 暂时仍走 `56855`。
3. 按应用级收尾方案处理旧实例，确认账务/后台工作安全后停止原容器，释放 `56854`。
4. 启动最终 HAProxy，直接发布原 `56854` 入口，后端指向 web-blue；保留既有 IPv4/IPv6 使用范围。
5. 完成唯一 master 的安全交接并验证后台任务接管，不让旧、新 master 的副作用任务无保护重叠。
6. 检查 HAProxy 直连路径，再把 Nginx upstream 改回 `127.0.0.1:56854` 并平滑 reload；已经经过 `56855` 的请求继续完成。
7. 保留旧容器及镜像供回退，不执行原 Compose 项目的 `down`，不重建 PostgreSQL、Redis 或共享网络。

直连端口释放与新入口启动之间存在维护窗口，旧容器未结束的直连流可能中断；时长以演练结果为准，**不承诺固定 1–3 秒**。短暂不可用的许可不等于允许丢失结算或退款。

初始 blue 的 `56855` 不在有连接时强行删除。下次发布使用不映射宿主端口的 green，确认 Nginx 与所有调用方均已离开 `56855`、旧请求结束后，再随 blue 正常退役去掉该临时入口。代理连接统计不覆盖绕过代理的临时入口，必须单独核查。

## 后续日常发布

1. 确认备用槽不接新流量、没有残留连接或应用工作；有残留则拒绝覆盖。
2. 完成兼容迁移，启动固定 digest 的候选 web 槽，等待业务就绪。
3. 发布锁保护下先持久化目标路由及操作日志，再通过 HAProxy 管理 socket 启用新槽、将旧槽设置为 drain；不重启入口。
4. 新 HTTP 请求进入新版；已有 SSE/WS 留在旧版。旧 WS 上的后续 turn 仍属于旧版工作，不发生连接迁移。
5. 同时确认旧槽代理会话/排队归零、无旁路连接、后台及账务工作收尾成功，才停止旧槽；超时保留，不强杀。
6. worker 的更新单独执行受控交接；两个 web 槽完成切换不代表后台版本也已安全更新。
7. 发布中断可检查 pending 日志并恢复或撤回；候选失败不得覆盖上一个成功版本的回滚记录。

不要靠非幂等 POST 自动重试或重新发送已经开始的 SSE 请求掩盖发布失败，以免重复上游计费。

## 回退边界

- 阶段一失败：新旧 schema/缓存仍兼容时，恢复 Nginx 到原 `56854`；保留候选证据，不盲删实例或数据。
- 阶段二失败：先确认端口占用、唯一 master 和数据库兼容性，必要时释放新入口、恢复原容器及域名路由。已经完成的数据库迁移不能由 `docker start` 撤销。
- 日常发布回滚：把新请求切到保存的上一个成功 image ID，保留当前版本在途连接直至安全排空。
- 不兼容 schema 或数据变化需要专门恢复方案；恢复旧备份可能丢弃之后的新业务数据，必须评估后决定，不能自动覆盖生产库。

## 发布执行器待实现能力

- 明确区分 `prepared`、`domain_on_blue`、`edge_on_56854`、`fully_managed`，每一步持久化状态并检查幂等性。
- 单机发布锁、固定 image ID/digest、角色和环境校验、端口占用及旁路检查。
- 首次两阶段切换、Nginx 配置检查/平滑 reload、失败保留、手动回退与中断恢复。
- 网络与应用双重排空判据；不把状态接口 200、固定 sleep 或 Docker healthy 当作业务收尾证明。
- 私有状态和备份不泄露密钥；日志只记录非敏感的版本、实例、状态和错误类别。
- 用合成后端验证普通 HTTP、SSE、WS、切流、回滚、进程中断、占用槽拒绝覆盖；另用隔离业务环境验证结算、退款、任务和数据库迁移。
